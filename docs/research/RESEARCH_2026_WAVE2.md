# Research wave 2: live voice agent, languages, voice tools, agent teams, design, ops

> 6 teams + principal engineer, Oct 2026. ⚠️ = page not opened.

## Live voice architecture

1. 1. On-device audio host (Expo dev build, custom native module): always-on mic only while a shift is active, with the OS echo cancellation, noise suppression and gain control (iOS voiceChat, Android VOICE_COMMUNICATION). Runs as an Android foreground service and with iOS background audio. A persistent notification and on-screen indicator show that listening is on.
2. 2. On-device gate (sherpa-onnx): Silero VAD on every frame plus keyword spotting. No wake word is needed. Audio leaves the phone only when speech is detected. A 300 ms ring buffer is replayed after reconnect so the first words are not lost.
3. 3. Session manager: opens or resumes a WebRTC session (LiveKit RN SDK plus Expo plugin; Pipecat RN client over SmallWebRTC as plan B) using a pre-warmed token, with reconnect in under 500 ms. The conversation window stays open for 20-30 s after the last turn, then closes. Billable time is about 30-60 active minutes per shift instead of 8 hours.
4. 4. Barge-in: VAD activity while the assistant is speaking stops text-to-speech playback on the phone immediately and sends an interrupt to the server. VAD thresholds are tuned per audio route (speaker vs car Bluetooth) to avoid false barge-ins.
5. 5. Server voice orchestrator: one Pipecat (BSD-2) pipeline per driver session, running inside the FastAPI backend. It uses Pipecat Flows (in core since 1.5) for shift states: start shift, driving, at stop, proof of delivery, end of day. Smart Turn v3.2 detects end of turn; for languages it does not cover (Maori, Samoan, Tongan, Tagalog) it falls back to a VAD silence timeout.
6. 6. Provider abstraction (speech-to-speech): the primary is Gemini Live native audio, the fallback is OpenAI gpt-realtime mini, and Grok Voice is watch-only. Model IDs are kept in config because Gemini Live 2.5 has a scheduled discontinuation on 2026-12-13. LLM calls go through the LiteLLM gateway for budgets and fallback.
7. 7. Language router (D3): the driver's language is detected at onboarding and stored as driver.lang (BCP-47, plus an optional second language); detection also runs on every utterance. Supported languages go speech-to-speech. Unsupported or poorly handled ones (te reo Maori, Pacific languages) go through a cascade: cloud speech-to-text, then the LLM, then cloud text-to-speech. The reply is always in the driver's language.
8. 8. Address canonicalisation: the LLM never writes an address itself. The resolve_stop tool fuzzy-matches spoken text against today's manifest and the LINZ address table (pg_trgm plus Double Metaphone in PostGIS) and returns the official English address ID. A per-session vocabulary pack (streets, suburbs, Maori place names, customer names) is sent as speech-to-text keyterms. Text-to-speech wraps addresses in an en-NZ span, and on screen they are shown with bidi isolation.
9. 9. Tool layer: one typed Pydantic registry is the single source for LLM function schemas, a FastMCP server (for tests and evals) and a generated TypeScript client used by UI buttons. Every UI action is a tool. In the live loop, tools are called in-process, with no MCP network hop. Each tool has a risk class (read, reversible, destructive, external), an idempotency key and a short spoken acknowledgement.
10. 10. Confirmation policy, enforced in the tool layer and never left to the prompt: read tools run immediately; reversible tools run and offer a 10 s spoken undo; destructive or external tools need the assistant to read back the target and the driver to say yes explicitly. Silence or noise means cancel. Replies are 12 words or fewer while the vehicle is moving, and lists are at most 2 items.
11. 11. Hands-free proof of delivery (D4): when the driver says 'delivered', the phone first writes a local event (event UUID, stop ID, GPS fix, distance to the geocoded address, timestamp, utterance hash) to a SQLite outbox, then syncs it. The server is idempotent per event UUID. If the driver is more than 150 m from the address, the assistant asks before recording. Photo, signature and barcode are optional and can be triggered by voice.
12. 12. Memory: start with mem0 on the existing Postgres (pgvector), scoped by driver_id, with three scopes: driver (language, habits), address/door (gate codes, safe-drop spots, dogs) and route. Move to Graphiti (time-stamped facts, needs Neo4j or FalkorDB) once fact versioning matters. At most 3 facts for the current stop are injected into context before arrival.
13. 13. Offline fallback: on loss of connectivity, the phone switches to sherpa-onnx speech-to-text (multilingual Whisper-small int8, downloaded once over Wi-Fi, with manifest hotwords), then a deterministic grammar plus a small intent classifier for about 15 core commands (delivered, failed with reason, next stop, navigate, call customer, repeat, undo, pause), then on-device text-to-speech (Kokoro where the licence allows, otherwise pre-generated prompts per language). The assistant announces limited mode, queues actions in the outbox and syncs later. The offline Canterbury map keeps navigation working.
14. 14. Cost per shift (prices are third-party figures, not verified): about 45 active minutes costs roughly $0.5-1.5 on Gemini Live or $1-3 on gpt-realtime mini, compared with about $30-38 if audio streamed continuously. Hard caps per driver per day are set in LiteLLM, and Langfuse cost events alert when cost per shift or per delivery goes over threshold.
15. 15. Battery and performance: budget about 5-8% per hour with VAD gating, show a car-charger prompt at shift start, and run a nightly Flashlight plus Maestro 10-minute voice session on a low-end Android phone. The SLO is p95 from end of speech to first audio under 800 ms, measured with Sentry spans (vad_end, stt_final, llm_first_token, tool_exec, tts_first_audio).
16. 16. Privacy (NZ Privacy Act 2020, IPP 3 and IPP 12): explicit consent for the always-on microphone and for sending audio offshore, listening only during an active shift, a 'pause listening' command by voice and button, no audio stored by default, transcripts kept for 30 days, all memory scoped per driver, and PII scrubbed from Sentry and PostHog.

## Design rules

1. 1. One in-house design system, 'Courier Base': Tokens Studio, then DTCG JSON, then Style Dictionary, then a Restyle theme. No raw hex or px values in components; lint fails the build on them.
2. 2. The driving screen shows at most 3 elements: next-stop address (English, 28pt semibold), ETA and distance (tabular numbers), and one primary action.
3. 3. Voice is a quiet persistent 64dp bottom bar with listening, thinking and speaking states. The main screen is never a chat-bubble interface.
4. 4. Every action the assistant takes appears as a toast with an Undo option (e.g. 'Delivered - 14 Riccarton Rd - Undo'), plus haptics and a short earcon.
5. 5. Neutral greyscale plus one brand accent. Green, amber and red are used only for status.
6. 6. Banned because they look AI-made: purple-blue gradients, glassmorphism, sparkle or star 'AI' icons, emoji in the UI, rounded-2xl cards on everything, and 'I'm your AI assistant!' copy.
7. 7. One icon set only: Material Symbols at weight 500 (24dp in lists, 32dp on the driving screen). Never mix icon sets on one surface.
8. 8. Type: Inter with tabular numbers for Latin; Noto Sans Arabic, Devanagari and CJK loaded on demand per locale. Body text at least 17pt.
9. 9. Tap targets at least 56dp, placed in the bottom thumb zone. No touch is required while moving (NZ handheld phone law).
10. 10. Contrast at least 7:1 for driving text. Automatic night theme (true-black surfaces) and a high-glare day theme.
11. 11. Motion tokens of 120, 200 and 300 ms with standard easing. No decorative loops. Reduce-motion is honoured, and the listening pulse becomes static.
12. 12. Full RTL mirroring for Arabic, Urdu and Farsi. Addresses and street names always stay LTR English, isolated with FSI/PDI bidi marks.
13. 13. All strings use ICU messages through i18next. Machine-translated strings are flagged needs_review, and a native speaker reviews ar, hi, zh, tl, sm and pa before release.
14. 14. Copy is short and imperative, with no exclamation marks and no filler. Error messages say what happened and what to say or do next.
15. 15. Proof-of-delivery UI: voice 'delivered' is the default. Photo, signature and barcode are optional chips, never blocking steps.
16. 16. The offline or limited mode state is always visible as one status chip, along with the sync queue count.
17. 17. Spoken replies are 12 words or fewer while moving, never more than 2 list items, and the assistant never reads the screen aloud.
18. 18. The customer tracking page and the end-of-day GST PDF use the same tokens (Style Dictionary CSS output), so the brand is the same across all surfaces.
19. 19. Every packages/ui component has Storybook stories (RTL, dark, large text, every state) and a screenshot test before merge.
20. 20. A human design-review gate applies to any PR that touches packages/ui. Agents do not free-generate screens; they implement from the approved specs and tokens.
21. 21. Monthly ride-along test with 5 Christchurch couriers. Targets: glance time under 2 s and voice-only task success for the top 10 tasks.
22. 22. Accessibility: screen-reader labels on every control, support for dynamic type up to 200%, and no colour-only status.

## Ops setup

- Errors, crashes and traces: Sentry SaaS (sentry-react-native with the Expo plugin and Hermes source maps uploaded via EAS; sentry-sdk on FastAPI). Distributed tracing links mobile voice spans to the backend. Release health gates EAS Update rollouts. Do not self-host (FSL licence).
- LLM and voice observability: Langfuse Cloud (EU or US region), with traces tagged by tenant, shift, language and tool. Speech-to-text and text-to-speech seconds are logged as cost events. A dashboard shows cost per shift and per delivery, and evals measure tool-call accuracy per language.
- LLM gateway: LiteLLM proxy, kept private and pinned to a version, with a virtual key per tenant, daily budget caps, RPM limits per driver, model fallback and a cost kill-switch.
- Product analytics and flags: PostHog EU cloud, with an event for each executed voice tool, voice-only vs tap funnels, and per-language flags to roll out new tools. Never record audio, and mask addresses and names in replay.
- Uptime: Uptime Kuma (MIT) on a separate small VPS, probing /healthz, /readyz (DB plus PostGIS), the LLM gateway, the voice signalling endpoint and the tracking page. Public status page, alerts to Slack and push.
- Performance CI: Reassure on every PR; a nightly Flashlight plus Maestro voice-shift run on a low-end Android phone (CPU, RAM, thermals, battery); Xcode Instruments for iOS; k6 load test of the voice and tracking endpoints before each release.
- Rate limiting and gateway: Cloudflare in front of the API, a Redis token bucket per driver in FastAPI, and LiteLLM limits. No Kong or APISIX at MVP stage.
- Webhooks: an internal outbox table first; add Svix (MIT or Cloud) when the first merchant integration exists. SMS for ETA messages goes through a single provider adapter.
- Incidents: Markdown runbooks in /docs, SEV1-3 levels and a postmortem template. Track work in Linear with GitHub links. Keep docs and ADRs in the repo.
- Internal automation, for example the ops Slack digest: n8n for internal use only. Customer-facing features such as the GST report must be built in FastAPI.

## Conflicts

- The research recommends continuous live voice (D1), but continuous streaming costs about $30-38 per shift. The founder's 'always live' requirement has to be met through VAD gating plus a conversation window, so it feels always-on while the billable audio is about 45 minutes.
- D3 promises 'all languages', but Smart Turn, Gemini and OpenAI native audio, and offline TTS (Kokoro has no Arabic, Tagalog or Samoan) do not cover te reo Maori or the Pacific languages well. Ship on the cascade path, label those languages 'beta', and test with real drivers before marketing the claim.
- D4 makes a spoken 'delivered' the proof of delivery, but in disputes it is weaker evidence than a photo. Store GPS, distance and a timestamp with it, ask when the driver is more than 150 m away, and tell platforms clearly what the evidence shows.
- The research reports disagree on memory: one recommends Graphiti (needs a Neo4j or FalkorDB graph database), another mem0. Decision: start with mem0 on pgvector to avoid new infrastructure.
- The research reports disagree on transport: LiveKit (needs a LiveKit server or Cloud) vs the Pipecat RN client over SmallWebRTC (20 stars, unproven on iOS in the background). Decision: use LiveKit RN as primary and spike SmallWebRTC.
- Model churn risk: gemini-live-2.5-flash-native-audio is scheduled for discontinuation on 2026-12-13, only about 2 months away. Keep provider and model IDs in config, and run an eval suite before each switch.
- Unverified pricing: Gemini, OpenAI realtime and Grok prices all come from third-party sources. I did not re-verify them with WebSearch in this run, so confirm them on the vendors' own pricing pages before committing a cost model.
- Licence: Silero VAD shows conflicting labels (MIT vs a CC BY-NC badge). Check the LICENSE file before shipping it inside sherpa-onnx.
- Licence: the LiveKit turn-detector model is under the separate LiveKit Model License, so use Smart Turn (BSD-2) instead. sherpa-onnx model licences vary per model.
- Licence: MMS-TTS, NLLB and Seamless are CC-BY-NC; Moonshine's non-English models are under a non-commercial licence; the SenseVoice model licence is custom. None of these can be bundled in a commercial app without legal review.
- Licence: piper1-gpl is GPL-3.0 and must not be bundled in the app. LibreTranslate is AGPL; avoid it.
- Licence: claude-task-master is Commons Clause; contains-studio has no licence; TEN framework has extra restrictions; Anthropic's document skills are source-available. Skip all of them.
- Licence: Sentry is FSL, Outline is BSL, n8n is under the Sustainable Use License, and OpenStatus, Plane, Loki and k6 are AGPL. Use them only as SaaS or internally, never embedded or modified for redistribution. LiteLLM has had security advisories, so keep it private and pin its version.
- Tokens Studio git sync needs a paid Pro seat. SF Symbols may only be used on Apple platforms.
- Privacy and ToS: hosted voice APIs send NZ driver audio offshore, which needs IPP 12 disclosure and consent. Also check each vendor's data-retention and training opt-out terms and the iOS App Store rules for background microphone use (the app must show it is recording and use it only for the declared purpose).
- Safety: NZ handheld phone law means no flow may require touch while the vehicle is moving.

## Always-on live multilingual voice agent (full-duplex, barge-in, tool calling, offline fallback)

**Recommendation:** Build a hybrid design where the phone gates the audio and the cloud handles conversation. The phone runs sherpa-onnx all shift: Silero VAD, keyword spotting, offline speech-to-text and text-to-speech, plus Smart Turn v3.2 for end-of-turn detection. It opens a cloud speech-to-speech session only while the driver is actually talking, or for an open conversation window of about 20-30 s after the last turn. Streaming 8 hours of raw audio to any realtime API is too expensive (8 h x about $0.06-0.08/min is roughly $29-38 per shift) and drains the battery. Gating the audio brings this to about 30-60 active minutes, roughly $1-4 per shift depending on model. Run the conversation on a Pipecat (BSD-2) server pipeline inside the existing FastAPI backend, with LangGraph tools exposed as function calls. Make the speech-to-speech provider swappable. Primary choice is the Gemini Live native-audio models, because they claim the widest language coverage at about $0.005/min in and $0.018/min out (third-party figures). Use OpenAI gpt-realtime-2.1-mini as the fallback and Grok Voice at about $0.08/min as an optional third option. Keep a cascaded path (speech-to-text, then an LLM, then text-to-speech) for languages that speech-to-speech handles badly, including Maori and any language the native-audio models do not cover. For transport, use the LiveKit React Native SDK with its Expo plugin (development build), or the Pipecat React Native client over SmallWebRTC. Echo cancellation and noise suppression come from the phone's WebRTC stack. The offline mode is fully on-device: sherpa-onnx speech-to-text, then a deterministic intent grammar for about 15 core commands (delivered, next stop, navigate, call customer, failed delivery with reason, pause), then sherpa-onnx text-to-speech. Actions are queued in a local outbox and synced later. The on-device grammar is also the safety net for proof of delivery: when the driver says "delivered", the app records the event locally with GPS and timestamp first, and cloud confirmation comes afterwards.

**Architecture:** 1) On the phone (Expo development build): a native audio module runs the always-on microphone with the phone's echo cancellation, noise suppression and gain control (iOS voiceChat mode, Android VOICE_COMMUNICATION). Silero VAD (sherpa-onnx) runs on every frame. When speech starts, the app opens or resumes a WebRTC session to the server (LiveKit RN, or the Pipecat RN client over SmallWebRTC). It closes the session after about 30 s of idle; with a pre-warmed token, reconnecting takes under 500 ms. A ring buffer replays the first 300 ms of speech after reconnect so no words are lost. Barge-in: VAD activity while the assistant is speaking stops playback on the phone immediately and sends an interrupt to the server. Run it as a foreground service on Android and with the background-audio capability on iOS. Android battery drain is tolerable with VAD gating, plus a car-charger prompt; budget about 5-8%/h and measure it.
2) On the server: a Pipecat pipeline per driver session. The default path sends audio to Gemini Live native audio with tool calls. Each tool maps to an existing FastAPI/LangGraph endpoint, for example mark_delivered(stop_id, method=voice|photo|signature), next_stop, navigate, notify_customer_eta, add_note, report_issue, day_summary. Tool responses are short and spoken. Language detection picks the path: for a supported language, the app sends speech straight to the provider; for an unsupported one (for example Maori), the cascade is cloud speech-to-text, then the LLM, then cloud text-to-speech, with a reply in the driver's language and addresses always read out in English.
3) Safety: confirm destructive actions by voice ("Delivered to 12 Riccarton Rd, right?"). Write events optimistically to a local SQLite outbox, so the server is idempotent per event UUID.
4) Offline: on loss of connectivity, switch to on-device sherpa-onnx speech-to-text (multilingual Whisper or SenseVoice model), then a grammar and small-intent classifier, then on-device text-to-speech. The app tells the driver it is in limited mode.
5) Cost per shift: about 45 active minutes, roughly $0.5-1.5 on Gemini Live or $1-3 on gpt-realtime mini; streaming continuously would cost about $30.

## All languages: multilingual STT with code-switching, multilingual TTS, language detection, React Native i18n and RTL, UI string translation, keeping addresses in official English

**Recommendation:** Use two tiers. (1) ONLINE (the normal case, needed for the live full-duplex assistant): a hosted realtime speech-to-speech or STT model with many languages, run through an open-source orchestrator (pipecat, BSD-2, or livekit/agents, Apache-2.0) so the vendor can be swapped. Language auto-detection runs per utterance. The LLM gets a fixed rule: answer in the driver's detected language, but copy street names, suburbs, postcodes and customer names exactly as they appear in the English manifest. (2) OFFLINE/ON-DEVICE fallback: sherpa-onnx (Apache-2.0), which the project already uses, running Whisper (MIT) multilingual small/turbo models, or SenseVoice for zh/yue/ja/ko/en. Pass a hotword/prompt list built from today's manifest street names so English addresses survive inside Arabic or Hindi speech. Text-to-speech: a cloud multilingual TTS when online. Offline, use sherpa-onnx with Kokoro (Apache-2.0) or MMS-TTS voices (check each model's licence; many MMS models are CC-BY-NC). Do NOT ship Piper's newer piper1-gpl (GPL-3.0) inside the app binary. UI: i18next + react-i18next (MIT) + expo-localization, I18nManager for RTL (Arabic/Urdu/Farsi), ICU plurals, and LLM-assisted machine translation of string catalogues at build time with human review for the top 6 languages. Avoid LibreTranslate (AGPL) and Meta Seamless/Omnilingual weights without checking their licences.

**Architecture:** 1) Language profile: at onboarding the driver says one sentence. The app detects the language (Whisper language ID through sherpa-onnx) and confirms by voice; the setting is stored as driver.lang (BCP-47) plus an optional second language, with auto-detection still running on each utterance. 2) Live path: Expo app -> WebRTC (LiveKit RN SDK) or a websocket -> pipecat/LiveKit agent on the FastAPI side -> a hosted realtime multilingual speech-to-speech model, or STT+LLM+TTS. Each session gets a 'vocabulary pack' built from today's manifest: street names, suburbs (Riccarton, Papanui, Hornby), customer names and Maori place names. It is sent as STT keyterms/prompt and as LLM context. 3) Address canonicalisation: the LLM never writes an address freely. The tool `resolve_stop(spoken_text)` fuzzy-matches against the manifest and LINZ address table (pg_trgm + phonetic/Double-Metaphone on PostGIS) and returns the official English address id. The text-to-speech output wraps addresses in an English-pronunciation span (SSML lang="en-NZ" where the vendor supports it). 4) Offline fallback: sherpa-onnx Whisper-small multilingual (int8, about 250MB, downloaded once over Wi-Fi), hotwords from the manifest, and a tiny intent grammar for 'delivered / next / call customer / failed' in the driver's language. Offline text-to-speech uses Kokoro or an MMS-TTS voice if its licence allows; otherwise short pre-generated prompts per language. 5) UI i18n: i18next + react-i18next + expo-localization. Keys live in /locales/{lng}/*.json. Use ICU, logical CSS (start/end) and I18nManager RTL with an app restart. Fonts: Noto Sans + Noto Sans Arabic/Devanagari/CJK subset. A CI step machine-translates new keys with an LLM, marks them 'needs_review', and a native speaker reviews ar, hi, zh, tl, sm, pa before release. The UI ships in about 10 languages; voice works in any language the realtime model supports. 6) Customer SMS and the ETA link use the CUSTOMER's language (default en-NZ), never the driver's.

## Voice-only control of the app: tools, confirmations, hands-free proof of delivery, always-listening privacy, and long-term memory

**Recommendation:** Build the always-on assistant as a Pipecat pipeline on the server, linked to the Expo app over LiveKit WebRTC. On the phone, sherpa-onnx with Silero VAD runs all the time on-device, so no wake word is needed and audio only leaves the phone when VAD detects speech while a shift is active. Smart Turn v3 decides when the driver has finished speaking, and it covers 23 languages including Arabic. Use a hosted speech-to-speech or STT-LLM-TTS model that handles any language. Expose every app action as one typed tool in a single registry, written once (Pydantic, then JSON Schema) and served to three consumers: the LLM's function calling, an MCP server through the official Python SDK (so the same tools can be tested and reused by other agents), and the app's UI buttons. Each tool has a risk class. Read-only tools and "delivered" run at once and give short spoken feedback, with an undo window. Destructive or external actions (cancel a job, message a customer, end the shift) need the driver to confirm out loud by repeating the target back. For memory, use Graphiti, which stores time-stamped facts per driver, address and door in Postgres-adjacent Neo4j/FalkorDB, or start with mem0 if the team prefers something simpler. Letta is a fallback only if a stateful-agent server is wanted. Do not use Zep Community Edition.

**Architecture:** 1) Tool registry (backend/tools/): each tool is a Pydantic model plus a handler, with these fields: name, description (short and imperative), args, risk (read | reversible | destructive | external), idempotency key, spoken_ack template, and ui_binding. From it, generate (a) the LLM function-calling schemas, (b) a FastMCP server, and (c) a TypeScript client, so every button in the UI triggers the same tool. Rule: there is no UI action without a tool. Starting tools: start_shift, end_shift, list_stops, next_stop, navigate_to, reorder_route, skip_stop, mark_delivered(stop_id, method=voice|photo|signature|barcode, note), mark_failed(reason), add_door_note, recall_door_notes, message_customer_eta (optional), scan_barcode, take_photo, repeat_last, undo_last, day_report(gst=true), set_language.
2) Confirmation policy, enforced in the tool layer and never left to the prompt. read: run straight away. reversible (delivered, skip): run, say "Delivered, 14 Elm St. Say undo to reverse", and keep undo open for 10 s or until the next stop. destructive or external (cancel job, SMS customer, end shift): the assistant reads back the target, for example "Text Mrs Smith ETA 4:10?", and an explicit yes is required. Silence or noise means cancel.
3) Hands-free proof of delivery: "delivered" records a server timestamp, GPS fix and distance to the geocoded address, the stop ID and an audio snippet hash. The driver can add a photo, signature or barcode by voice ("take photo" opens the camera and fires the shutter by voice). If GPS is more than 150 m from the address, ask before recording.
4) Voice UX for driving: replies of 12 words or fewer while the vehicle is moving (speed taken from GPS), no lists longer than 2 items, no reading from the screen, and numbers spoken in the driver's language. Addresses always stay in official English. Barge-in stops TTS immediately.
5) Listening without a wake word: listening only happens while a shift is active and is shown by a persistent notification and indicator. On-device VAD means raw audio is sent only when speech is detected. Do not store audio by default; transcripts are kept for 30 days. There is a voice and button command "pause listening". Disclose all this under the NZ Privacy Act 2020 IPP 3.
6) Memory: three scopes, all keyed by driver_id: driver (language, habits), address/door (gate codes, safe-drop spots), route (traffic patterns). Before each stop, retrieve that stop's address memory and inject it into the context as at most 3 facts.

## Company-grade product design (not AI-looking): design systems, tokens, icons, type, motion, QA, process

**Recommendation:** Build one small in-house design system called "Courier Base" instead of adopting a full UI kit. Use Uber Base and Apple HIG/Material 3 as reference for rules only, not as code dependencies. Run tokens through a single pipeline: Tokens Studio (Figma) to JSON to Style Dictionary 4/5 to a TS theme consumed by Shopify Restyle. Use Material Symbols (Apache-2.0) as the one icon set, with Lucide as fallback. Never mix icon sets. Typography uses Inter (OFL) for Latin, plus Noto Sans per script (Arabic, Devanagari, CJK) from google/fonts, because D3 requires every language. Motion uses Reanimated with a short token set and honours reduce-motion. QA uses Storybook RN, screenshot diffs, and a monthly ride-along usability test with real Christchurch couriers. Things that make a UI look AI-made and are banned: purple-blue gradients, glassmorphism, sparkle/star "AI" icons, emoji in UI, rounded-2xl cards on everything, generic chat bubbles as the main screen, and lorem-style friendly copy. The main screen is a driving surface (next stop, ETA, one status), and voice state is a quiet persistent bar, not a chatbot. GitHub API metadata (stars, licence) was only partly confirmed through search. Licences listed come from my knowledge where the search returned none, so treat those fields as needing a recheck.

**Architecture:** Pipeline: Figma (Tokens Studio) to /design/tokens/*.json (DTCG) to Style Dictionary to packages/ui/theme.ts (Restyle), web CSS vars and PDF report styles. Components live in packages/ui and each has a Storybook story and a screenshot test.

Concrete rules:
1) The driving screen shows a maximum of 3 elements: next stop (address in English, 28pt semibold), ETA/distance (tabular numbers), and a single primary action. Everything else is reachable by voice.
2) Tap targets are at least 56dp while driving (above the 44/48 minimum) and sit in the thumb zone at the bottom.
3) Contrast is at least 7:1 for driving text. Provide an automatic night theme (true dark #000-ish surfaces) and a high-glare theme.
4) Colour: neutral greyscale plus one brand accent; semantic green, amber and red only for status. No gradients, glass, or sparkle icons.
5) Voice is a persistent 64dp bottom bar showing listening, thinking and speaking states with a waveform. The live transcript is shown in the driver's language. Every action the assistant takes appears as a confirmable toast ("Marked 14 Riccarton Rd delivered - Undo"), with haptics and a short earcon.
6) Proof of delivery: voice "delivered" records a timestamp and GPS; photo and signature are optional chips.
7) i18n: full RTL mirroring for Arabic and other RTL languages. Addresses and street names are always LTR English, isolated with bidi marks. Strings use ICU messages.
8) Motion: 120/200/300ms, standard easing, no decorative loops. Honour reduce-motion.
9) Copy is short and imperative. No exclamation marks, no "I'm your AI assistant!".
10) Process: weekly design critique; a design-review gate on PRs touching packages/ui; an accessibility checklist; a monthly ride-along test with 5 Christchurch couriers measuring glance time under 2s and task success by voice only.

## Monitoring, performance and company-level integration: mobile performance, app health and real-user monitoring, uptime and status pages, incidents, logs, LLM and voice cost, webhooks and integrations, API gateway and rate limits, project management, internal docs

**Recommendation:** Keep it lean, with five pillars and only one tool for each. (1) Errors, crashes, real-user monitoring and traces: Sentry SaaS (sentry-react-native plus sentry-sdk for FastAPI). Use Sentry's free or Team plan. Do not self-host it, because self-hosted Sentry is under the FSL licence and costs a lot to run. (2) Product analytics, feature flags and session replay: PostHog Cloud on the EU region. (3) LLM, voice and agent tracing and per-shift cost: Langfuse, either Cloud or self-hosted using the MIT core. Route every LLM call through a LiteLLM proxy, which handles per-tenant budgets and rate limits and lets us swap models. (4) Uptime and the public status page: Uptime Kuma (MIT) self-hosted on a small VPS. Use OpenStatus SaaS only if we want a hosted status page, because the self-hosted version is AGPL. (5) Performance gates in CI: Reassure for component render regressions, plus Flashlight or Maestro runs on a real low-end Android device for FPS, CPU and RAM during a voice session. Webhooks to customers and partners (ETA SMS, tracking links, merchant integrations): use Svix, the MIT server or Svix Cloud, rather than building our own. Internal automation such as end-of-day GST reports and Slack alerts can go in n8n, but its Sustainable Use licence does not allow embedding it in the product. Use it for internal work only. Linear (SaaS) for the project. Docs live in the repo (/docs Markdown plus ADRs) and are published as a wiki. Choose Outline only if non-engineers need a wiki, and note it is under BSL. Skip Loki, SigNoz, Kong and APISIX at MVP stage. FastAPI middleware plus LiteLLM plus Cloudflare covers the gateway and rate limiting until there is real scale.

**Architecture:** Telemetry contract: every request and voice turn carries trace_id, tenant_id, driver_id (hashed), shift_id and lang. Mobile: Sentry spans for the voice pipeline (vad_end to stt_final to llm_first_token to tool_exec to tts_first_audio). The SLO target is p95 barge-in-to-response under 800 ms. A PostHog event is sent for each executed voice tool. Backend: FastAPI with sentry-sdk and OpenTelemetry. LangGraph runs go to Langfuse through a callback. All model calls go through the LiteLLM proxy, with a virtual key per tenant, a daily budget, and an RPM limit per driver. STT/TTS seconds are logged as Langfuse cost events, giving a daily dashboard of cost per shift and cost per delivery, with alerts when either goes over threshold. Rate limiting: Cloudflare in front of the API, a Redis token bucket in FastAPI per driver, and LiteLLM limits for LLM calls. Uptime Kuma runs on a separate small VPS and probes /healthz, /readyz (DB plus PostGIS), the LLM gateway and the public tracking page. Its public status page and alerts go to Slack and PagerDuty-lite (push). Incidents: a Markdown runbook in the repo, severity levels SEV1-3, and a postmortem template. CI: Reassure on every PR, a nightly Flashlight plus Maestro voice-shift run on a physical Android device, and k6 before releases. Webhooks: an internal outbox table first, with Svix once partners exist. Project and docs: Linear (cycles, GitHub links) and /docs plus ADRs in the repo.
