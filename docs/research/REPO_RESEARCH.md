# Repo research by area (team research, Oct 2026)

> Produced by 8 area researchers and 1 critic. Repos marked ⚠️ could not be opened in this session. Re-check last-commit dates before installing.

## Final unified stack (critic)

- Mobile: Expo SDK (pinned, New Architecture, dev client) + expo-router; start from the obytes template only if its 2026 activity checks out, otherwise use create-expo-app; Unistyles 3; Reanimated 4; @gorhom/bottom-sheet; FlashList v2; expo-haptics; expo-location + expo-task-manager
- Maps: Geofabrik NZ PBF, cut to Canterbury with osmium, then planetiler (Protomaps profile) to canterbury.pmtiles, downloaded on Wi-Fi with expo-file-system and rendered by @maplibre/maplibre-react-native (pinned) with the Protomaps style; territory-only aerial raster PMTiles built from the LINZ/AWS COGs (CC BY 4.0); OSM and LINZ attribution shown in the app
- On-device voice: sherpa-onnx through our own thin Expo module (streaming zipformer, Silero VAD, KWS for delivered/next/undo, Piper TTS); whisper.rn as a second pass over buffered segments; expo-speech-recognition as the fallback with contextualStrings; a custom Expo module for earbud MediaSession/MPRemoteCommandCenter that owns the audio session
- Address correction: LINZ NZ Addresses + Suburbs/Localities (Canterbury) in PostGIS with pg_trgm; RapidFuzz + jellyfish + our own Māori/NZ lexicon; deterministic diff report; driver confirmation only for an invalid number, a street in two suburbs, a point outside the territory, or low ASR confidence; a Canterbury slice in on-device SQLite for offline matching
- Backend: FastAPI + LangGraph (single state machine) + Postgres/PostGIS/pgvector on Supabase or RDS in ap-southeast-2; Arq on Redis for LINZ refresh and jobs; LiteLLM proxy (MIT features only) with Pydantic tool schemas; Deepgram Nova-3 en-NZ with keyterms as the optional online STT; Pipecat only if server-side realtime voice is kept
- Routing: Valhalla (Canterbury tiles) + VROOM v1.15 for stop ordering + OR-Tools for driver-rule constraints; learned entry points override the stop coordinates
- Sync: PowerSync (self-hosted, FSL accepted) with the op-sqlite adapter as the single local database; FastAPI stays the write authority
- Scanning (phase 2): VisionCamera v5 + official v5 barcode package + our own ML Kit text v2 Nitro plugin; cloud vision LLM fallback with PII cropping
- Quality and ops: Langfuse (self-hosted), promptfoo + a recorded NZ-accent golden set, Sentry, PostHog (PII masked), Jest/RNTL, Maestro, Playwright, EAS Build/Update + expo-github-action@v8
- Dashboard and dev tooling: nextjs/saas-starter on the same Postgres, Stripe NZD + Stripe Tax; Claude Code + anthropics/skills + project .claude/skills; repomix. Avoid: Porcupine, openWakeWord, RNTP v5, Nominatim public API, legend-state, moti, react-native-carplay, bolt.diy/dyad, Phoenix

## Gaps

- The deterministic correction report is missing. Nothing produces the post-dictation 'you said X, I corrected it to Y' summary as a list that is both spoken and shown on screen, and the driver cannot accept or reject each change. Build it ourselves: a FastAPI endpoint that diffs the RapidFuzz/LINZ candidate against the raw ASR text, with a Pydantic schema and a FlashList review screen. The LLM may phrase the summary but must never pick the address.
- The double-check rule is not written down anywhere. Only these cases should go to driver confirmation: (a) the house number does not exist in that street's LINZ range, (b) the same street name exists in two or more suburbs, (c) the point falls outside the run's territory polygon, (d) the ASR word-level confidence is below the threshold. Everything else is auto-corrected silently and then reported in the summary.
- No Māori and NZ street-name pronunciation lexicon exists, and no repo provides one. Build our own table from the LINZ road names and Te Taura Whiri/LINZ macronised names, then feed it to sherpa-onnx hotwords, Deepgram keyterms and the jellyfish phonetic keys.
- No real NZ-accent test set exists. Record 200 or more Canterbury addresses in a van to benchmark WER (sherpa, whisper.rn, moonshine, Deepgram) and to serve as promptfoo golden tests. Without it, every STT choice is a guess.
- Offline address correction on the phone is not covered. If the phone is offline while dictating, correction is impossible unless a Canterbury slice of LINZ addresses (about 250k rows) is shipped to SQLite with an FTS5/trigram index and a JS fuzzy matcher. Decide whether correction is server-only (queue the job) or also on-device.
- Nothing covers the LINZ data pipeline. Pulling the LINZ Data Service WFS/changeset with an API key needs a scheduled loader, for example an Arq cron plus ogr2ogr or the LINZ 'lds' changeset API. No repo was chosen for this.
- No authority boundary data was chosen for Canterbury. The plan needs a LINZ/Stats NZ territorial-authority or suburb-locality polygon layer (NZ Suburbs and Localities, CC BY) to clip the data and to detect addresses outside the area.
- Learned door and entry points have no component. Store them in a PostGIS table with a per-address override point and use them as the Valhalla/VROOM stop coordinate. This is custom code.
- Background location and geofenced auto-arrival are not covered: expo-location background plus expo-task-manager is needed and was not listed.
- The driver-rules DSL is not designed. It needs to take rules managed by voice (for example 'always do X before Y', 'skip suburb Z on Fridays') and turn them into VROOM/OR-Tools constraints. LangGraph tool schemas exist, but there is no rule store or compiler.
- Auth and multi-tenant design are undecided: Supabase Auth versus the auth that ships with saas-starter versus PowerSync JWT. A single identity provider is needed.
- No NZ Privacy Act and app store compliance item exists: the privacy policy, mic and location purpose strings, iOS background audio justification, and a data retention policy for recipient addresses.

## Conflicts

- Two backend stacks (Pipecat Flows versus LangGraph): the brief names LangGraph, and the voice research recommends Pipecat with pipecat.flows as the state machine. That gives two orchestrators. Pick one: Pipecat for the realtime audio transport only (when it is online), with LangGraph owning the business state machine for dictation, correction and delivery. Alternatively, drop server-side streaming voice in v1, since dictation is on-device.
- Online and offline STT paths conflict: the voice-agent area streams audio to Deepgram, while the on-device area runs sherpa-onnx and whisper.rn. The brief requires offline-first, so on-device STT must be the primary path and Deepgram an optional enhancement used when there is coverage. Otherwise the correction step depends on connectivity.
- Two voice wrappers point at the same mic: expo-speech-recognition, react-native-sherpa-onnx and whisper.rn all want the AVAudioSession/mic. Running them together with the custom earbud MediaSession module will fight over audio focus. Use a single owner module for the audio session.
- Two sync paths and two SQLite libraries: PowerSync (which ships its own SQLite through @powersync/react-native or op-sqlite adapters), expo-sqlite, op-sqlite, and TanStack Query persistence. Pick PowerSync with its op-sqlite adapter as the single local database, and use TanStack Query only for online-only calls. Do not also persist lists in the Query cache.
- PowerSync licence: I verified it is FSL-1.1-ALv2 (source-available; each version becomes Apache-2.0 after two years). It is fine for self-hosted, non-competing use, but the research marked it 'use' as if it were open source. Alternatively, use PowerSync Cloud (paid). Record the decision.
- MapLibre RN v10 versus New Architecture requirements: Unistyles 3 and Reanimated 4 require the New Architecture, VisionCamera v5 and the pedrol2b plugin require RN 0.86+ and Nitro, and maplibre-react-native v10 is still in progress. The Expo SDK, RN version, MapLibre version and VisionCamera v5 must all line up in one compatibility matrix before any code is written. That needs a spike build on a real iOS and Android device, including PMTiles on iOS.
- Routing is duplicated: Valhalla appears twice (maps and backend), and OSRM and GraphHopper are listed as alternatives. Settle on Valhalla for the matrix and directions, VROOM for ordering, and OR-Tools only for constraints VROOM cannot express. Drop OSRM and GraphHopper.
- Too many observability tools: Langfuse plus Sentry plus PostHog, while Phoenix and Opik are also mentioned. Keep Langfuse for LLM tracing, Sentry for errors and PostHog for analytics. Drop Phoenix (Elastic-2.0) and Opik.
- Licence issues for a commercial product: osmium-tool is GPL-3 (fine as a backend CLI, but never bundle it). The silero-vad licence badge conflicts with the sidebar (verify the LICENSE file is MIT). react-native-track-player v5 is commercial (avoid). openWakeWord models are NC (avoid). LiteLLM enterprise/ and Langfuse ee/ are not MIT. OSM ODbL and LINZ CC BY 4.0 require on-screen attribution.
- Imagery approach conflicts with the LINZ terms: bulk-caching tiles from LINZ Basemaps under a standard key breaks its rate limits and terms. Build territory-only raster PMTiles from the LINZ/AWS open-data COGs instead (CC BY 4.0, allowed). Tell the user the plan downloads the full NZ PBF from Geofabrik, cuts Canterbury, and double-checks it against LINZ.
- Address matching splits across the backend (RapidFuzz/jellyfish in Postgres) and an offline phone matcher. Use one normaliser spec and one lexicon, shared as versioned data, so the corrections agree in both places.

## Offline maps for New Zealand (focus: Canterbury/Christchurch): vector tiles, aerial imagery, Expo rendering, routing tiles

**Recommended:** Pipeline: (1) Source: Geofabrik new-zealand-latest.osm.pbf (about 400 MB, updated daily, ODbL). (2) Server-side cut: run osmium extract with a Canterbury bbox or polygon (roughly 171.0,-44.6 to 173.9,-42.0) to produce canterbury.osm.pbf. (3) Vector tiles: run planetiler with the Protomaps basemap profile (or OpenMapTiles schema) to produce canterbury.pmtiles at z0-15. That is tens of MB. A faster alternative is `pmtiles extract` with --bbox on the Protomaps daily planet build. (4) Imagery: LINZ Basemaps aerial is CC BY 4.0, and Christchurch urban is 7.5 cm (2023). Do NOT bulk-scrape the standard key, which is capped at 1,000 tiles/min, 1M/month and renewed every 90 days. Request a LINZ developer key, or build a raster PMTiles/MBTiles for the delivery territory only (about z12-18) from the LINZ Data Service / AWS open-data COGs using gdal plus pmtiles convert. The national 10 m Sentinel-2 layer is the low-zoom fallback. (5) Phone: Expo dev build (config plugin, not Expo Go) with @maplibre/maplibre-react-native and a MapLibre style (Protomaps basemaps style, or a lightweight OpenFreeMap-derived style) pointing at a local file (pmtiles://file://...). The file is downloaded once on Wi-Fi into the documentDirectory via expo-file-system. Offline packs do not apply to PMTiles sources: ship the file instead. (6) Routing: build Valhalla tiles from the same canterbury.osm.pbf on the backend (FastAPI calls Valhalla for optimised multi-stop routes/ETA). On-device routing is optional later, using a Valhalla tile tar. OSRM is a second choice. Show 'Sources: LINZ CC BY 4.0, (c) OpenStreetMap contributors' attribution in the app.

## NZ address data, geocoding and auto-correction (Canterbury focus)

**Recommended:** Use the LINZ NZ Addresses layer (CC BY 4.0) as the reference, clipped to the Canterbury region, and load it into Postgres/PostGIS. Refresh it weekly using the LINZ Data Service changeset API. Build these indexes: pg_trgm GIN on a normalized street name, plus suburb, unit, number, number suffix and postcode, and a phonetic key column filled with jellyfish metaphone/NYSIIS. Add a Māori-aware normaliser that removes macrons and maps spoken forms (for example 'Wakatipu', 'Papanui', 'Ōpāwaho') to canonical names. Score candidates in Python with RapidFuzz (token_set_ratio and JaroWinkler) combined with the phonetic match and a check that the number exists in that street's range. The result is a confidence value plus a diff list ('street: Papa Nui Rd -> Papanui Road; suburb added: Merivale'). Only addresses that are actually ambiguous go to LLM or driver confirmation: a missing house number, the same street in two suburbs, a point outside the run's territory polygon, or a low ASR score. libpostal is an optional pre-parser. Photon or Pelias, loaded with the LINZ CSV, is an optional fallback for free-text search. Addressfinder or the NZ Post API is only a paid tie-breaker (for example for PO boxes or deliverability), not the core.

## On-device voice for React Native/Expo: offline streaming STT, VAD, keyword spotting, offline TTS, earbud media-button capture, background audio

**Recommended:** Build on sherpa-onnx (Apache-2.0, v1.13.8 released 2026-09-10) as the single on-device voice engine. It covers streaming zipformer STT, Silero VAD, keyword spotting ("delivered", "next", "undo") and offline TTS (Piper/Kokoro voices), all inside one native library. Use XDcobra/react-native-sherpa-onnx (MIT, v0.4.4) as the RN binding, with an Expo config plugin and a dev client (not Expo Go). It is young: 40 stars, and its VAD is only scheduled for 0.7.0. So budget for forking it or writing a thin Expo Module over sherpa-onnx's own Kotlin and Swift APIs, and pin versions. For bulk address dictation, add whisper.rn (MIT, v0.7.4, realtime transcriber with Silero VAD) as a second pass that re-transcribes the buffered segments, or moonshine-ai/moonshine (MIT streaming English models). The noisy-van accuracy matters more than raw latency, and the backend then corrects the text against LINZ/NZ address data. Keep expo-speech-recognition (MIT, v58 released 16 Oct 2026) as a fallback: it uses Apple/Google on-device engines (iOS 17+, Android 13+) and adds contextualStrings biasing, which helps with Christchurch street names. Do not use Porcupine because of its AccessKey and commercial-licence terms, and do not ship openWakeWord's pretrained models (CC BY-NC-SA). Use sherpa-onnx KWS for hands-free commands instead. For earbud play/pause single, double and long press, write a small custom Expo Module: MPRemoteCommandCenter plus AVAudioSession .playAndRecord with allowBluetooth on iOS, and a MediaSession callback inside a foreground service on Android. Avoid react-native-track-player v5, which now requires a paid commercial licence; v4 (Apache-2.0) is the only free option.

## Real-time voice agent + LLM layer (server side)

**Recommended:** Use Pipecat (BSD-2, v1.12.0 released Sep 2026) as the voice pipeline in the Python/FastAPI backend, with built-in pipecat.flows for the state machine (dictation mode with the assistant silent, then correction/report mode, then delivery mode). Don't use the archived standalone pipecat-flows repo. Use Deepgram Nova-3 streaming STT with language en-NZ and keyterm prompting. Load the keyterms per run from the PostGIS address table (Canterbury street and suburb names for that territory). Keep Speechmatics (custom dictionary) as an A/B fallback. Use Cartesia or ElevenLabs Flash for TTS, with self-hosted Kokoro as a low-cost or offline fallback. Route every LLM call through a self-hosted LiteLLM proxy (MIT core; enterprise/ features are under a commercial licence), and use strict JSON-schema tool calls validated with Pydantic, or Pydantic AI inside LangGraph nodes. Address correction must never come from the LLM's own guess: the LLM calls a geocode/validate tool that queries LINZ data, and the "you said X, I corrected it to Y" report is built from that tool's diff. Trace and score with Langfuse (self-hosted), and run promptfoo regression evals in CI on a set of recorded NZ-accent dictations. Pick LiveKit Agents instead only if you want LiveKit's WebRTC SFU and its turn-detector model; that model has its own LiveKit Model License.

## On-device parcel label scanning (continuous barcode + address OCR, multiple labels per frame)

**Recommended:** Use VisionCamera v5 (mrousavy/react-native-vision-camera, Nitro-based) as the camera layer, with its official split-out react-native-vision-camera-barcode-scanner package for continuous multi-barcode detection. ## Backend, routing and offline sync

Use Expo push notifications, Sentry for error tracking and PostHog for product analytics, with PostHog on EU or self-hosted and PII masked.

Test with Jest and React Native Testing Library for units, Maestro for mobile end-to-end flows (dictation list, voice "delivered", offline mode) on EAS or Maestro Cloud, and Playwright for the web dashboard. For the dispatcher/admin dashboard, start from nextjs/saas-starter (Next.js, Postgres, Drizzle, Stripe, MIT). Point it at the same Postgres/PostGIS as the FastAPI backend, and create Stripe Prices in NZD with GST handled by Stripe Tax. Do not use prompt-to-app builders for the production app. bolt.diy and dyad are fine for throwaway UI mockups only.

**Risks:**
- GitHub API access was blocked in this session and the repo pages did not show commit dates, so 'commits in 2026' is unconfirmed for every repo. Check the commits tab before adopting.
- Headroom's token-saving claims are self-reported and vary widely. Measure on real sessions first.
- Third-party skill and agent repos can carry prompt-injection or unsafe shell instructions. Review every SKILL.md before installing.
- alirezarezvani/claude-skills shows inconsistent star counts (28.3k in the sidebar vs 5.2k in the README).
- Prompt-to-app builders (bolt.diy, which is in maintenance mode, and dyad, which has FSL-licensed parts) are not suitable for a production offline-first voice app.
- Expo Agent status was not verified in this run.
- EAS Build/Update and Maestro Cloud are paid hosted services at scale. Budget for them.
- Stripe NZD billing needs Stripe Tax set up for NZ GST. The starters are not set up for this out of the box.
