Two things must not be conflated. **Crash reporting** (a native/JS crash reaches a server, with a stack trace and a release tag) is a different product from **product analytics** (an aggregate event like `stop_delivered`) and different again from **tracing** (a span tree for one request). And **OTA** (shipping a new JS bundle to phones that already have the app) is a different product from **CI/CD** (building and testing that bundle). V4 §6.6 names four tools — GlitchTip, PostHog, OpenTelemetry, Langfuse — one per job; our research confirms that mapping and adds a fifth, `expo-observe`, which is new in SDK 58 and does the mobile half of it inside the SDK we already ship.

### 6-month star trend — method note (proxy, as V4 §12.3 permits)

The star *timeline* is not readable with the token in `.env.local`: `GET /repos/{o}/{r}/stargazers` returns **HTTP 403 "Resource not accessible by personal access token"** (re-verified 2026-10-21). **Every "stars gained in 6 months" figure is therefore UNVERIFIED.** The proxy used throughout is the one §12.3 prescribes: **releases in the last 6 months · commits in the last 90 days · distinct human maintainers in 90 days** (bot/dependabot excluded). Where a repo's releases are cursor-paginated past 100 we write "100+".

### 3.1 Expo OTA — `expo/expo` + `expo-updates` (C1, C2, C5, A25)

**What I read.** `packages/expo-updates/README.md` in the repo (verbatim): *"The `expo-updates` module enables your app to manage remote updates to your application code. This module works with a server that implements the [Expo Update protocol]. The [EAS Update] hosted service implements this protocol. To build a custom server that implements the protocol, see the example server source code here"* → `expo/custom-expo-updates-server`. `packages/expo-observe/README.md` (the 2026 newcomer). The Expo docs **Deploy updates** (modificationDate 2026-08-11), **Rollouts** (2025-07-07), **Rollbacks** (2025-03-03), **End-to-end code signing** (2026-07-21) and **EAS Workflows → pre-packaged jobs** (2026-08-05) — all read in full, plus `expo.dev/pricing` and `docs.expo.dev/billing/usage-based-pricing`.

**The release vocabulary, exactly as documented.** A **channel** is what a binary points at; a **branch** is a stream of updates under a channel; a **runtime version** is what selects which update a device accepts. The recommended configuration is `"runtimeVersion": { "policy": "appVersion" }` and the docs are explicit: *"the 'fingerprint' policy is experimental and not yet widely recommended."* A build is bound to **one** channel forever (*"you cannot change the channel embedded in a build after you create it"*), but from SDK 54 **channel surfing** lets a release build request a different channel at runtime.

**Rollout — the mechanism that makes OTA safe for us.** Two kinds. *Per-update*: `eas update --rollout-percentage=10`, then `eas update:edit` to move the percentage, and `eas update:revert-update-rollout` to undo. The rules that matter: *"Only one update can be rolled out on a branch at one time"*, and *"When a rollout is in progress, it must be ended … before a new update (with the same runtime version) can be published. This prevents accidentally clobbering the rollout."* *Branch-based*: `eas channel:rollout` moves a percentage of a channel's users onto a new branch; *"Only one branch can be rolled out on a channel at a single time"*, and while a rollout is in progress **`eas update --channel` is not usable** — you must publish to the branch.

**Rollback — two kinds.** `eas update:rollback` either **re-publishes a previously-published update** to the channel, or **instructs the client to run the update embedded in the build**. *"Upon publishing again after a rollback, all clients will receive the new update."* That is the whole kill-switch story: publish → watch → rollback → publish the fix. No rebuild.

**Code signing — the part we must not skip.** `expo-updates` supports end-to-end public-key signing: the client **verifies the signature against a certificate embedded in the binary before applying the update**, so *"ISPs, CDNs, cloud providers, and even EAS itself cannot tamper with updates."* The private key never leaves the machine (`eas update --private-key-path`). Key rotation is a documented procedure and a new certificate means a **new runtime version**. The gate: **"EAS Update Code Signing is only available to accounts subscribed to the EAS Production or Enterprise plans"** — that is a paid-plan requirement and a founder-approval item.

**The EAS Workflows job types we would use** (from the pre-packaged-jobs doc): `build` (outputs `build_id`, `fingerprint_hash`, `runtime_version`, `channel`), `fingerprint`, `get-build`, `submit`, `testflight`, `update` (params `channel`, `branch`, **`rollout_percentage`**, `private_key_path`, `upload_sentry_sourcemaps`), **`update-rollout`** (params `update_group_id`, `rollout_percentage`), `branch-delete`, `require-approval`, and a **`maestro`** job (params `build_id`, `flow_path`, `shards`, `retries`, `retry_failed_only`, `record_screen`, `include_tags`/`exclude_tags`, `maestro_version`, `android_system_image_package`, `device_identifier`, `output_format: junit`) — marked **alpha** in the docs. Two details are gold for us: the `update` job has an `after_update` hook with a built-in **`eas/posthog_upload_sourcemaps`** function (PostHog and Expo are first-class partners — that is the same PostHog we are adopting), and the `update` job's `upload_sentry_sourcemaps` parameter *auto-detects `@sentry/react-native`*.

**Commits (2026-10-01 → 2026-10-20, `packages/expo-updates` path).** `4c90d63` 2026-10-15 "Version packages (main) (#51578)"; `36cc765` 2026-10-15 "Upgrade React Native to 0.88.0 (#51613)"; `8eca738` 2026-10-14 "Upgrade React Native to 0.88.0-rc.6 (#51555)"; `e180d56` 2026-10-07 "chore(internal-scripts): Rename `expo-module-scripts` to `@expo/internal-scripts` [2/2] (#51221)"; `c0e95f4` 2026-10-05 "chore(pkcs12,cli,updates): Bump `@expo/code-signing-certificates` and `node-forge` (#51085)" ← *the code-signing certificate library is the one `node-forge` advisory (accepted in CONSTRAINTS.md) comes from*; `88dc392` 2026-10-02 "[workspace] Upgrade `jest` to `^30.0.0` (#50427)".

The *risk* is not the mechanism, it is **our own discipline**: a bad JS bundle reaches every driver in minutes. The mitigations are exactly the ones Expo documents — signed updates, one rollout at a time, the rollback command, and a `preview` channel that only the team sees.

**Our own flows, read today.** `.maestro/smoke.yaml` (`launchApp` → `extendedWaitUntil` `today-screen` 60 s → `assertVisible: "Good morning"`), `today-list.yaml` (asserts `Delivered` / `Remaining` / `Success Rate`, then `takeScreenshot: "today-list"`), `stops.yaml` (tap `Stops` → `stop-2` → `assertVisible: "Riccarton"` → `takeScreenshot: "stop-detail"`), `map.yaml` (tap `Map` → `map-screen` → `takeScreenshot: "map"`), `compat.yaml` (`openLink: "courier://compat"` → a conditional `runFlow` for the microphone permission → six `assertVisible` on the native module ids → `takeScreenshot: "b7-compat"`). **Every flow already takes a screenshot; none asserts one.** So the visual-regression gate is a **one-word change** (`takeScreenshot` → `assertScreenshot` + a baseline) plus a diff step — not a new tool, not a new vendor.

**The distribution channel — the thing sprint #1 got wrong.** npm `maestro` has **5 versions**, the latest **2.1.1 from 2020-09-08**. The real distribution is the GitHub release binary, tagged `cli-<version>`, installed by `get.maestro.mobile.dev` — the script our `android-e2e.yml` downloads, prints and executes (never piped into a shell), which is exactly the V4 §7 rule. **We must pin the CLI version in CI**, because `get.maestro.mobile.dev` with no argument installs *latest*, and the newest CLI changes the driver APKs with it.

**Maestro Cloud, for the record.** $250 per device per month (Android/iOS) or $125 per browser per month (web), unlimited hosted runs, priced by max concurrent executions; the local CLI, Studio, Viewer and MCP are free and open source. At our size that is 30× our entire current monthly Actions allowance, for a device cloud we do not need — the emulator is a 2-core Linux job.

**Verdict.** **Keep Maestro, and make it do the visual regression too.** `assertScreenshot` + `reg-cli` gives us the design gate (day/night, small/large, 200 % text) with **no second vendor and no screenshot leaving our CI**, which is what CONSTRAINTS.md asks for. The cost is the tap latency (#3694) and the 255-byte artefact-name rule (#3682) — both documented, both watchable.

## 6. Decision

**1. Observability — three tools, three jobs, one collector, all self-hostable.**

- **Mobile telemetry and performance: `expo-observe` (SDK 58).** It is already in our SDK, MIT, open-source, and speaks OTLP with a **replaceable endpoint**. It measures **TTR and TTI on real phones** — the exact 2 s cold-start budget in CONSTRAINTS.md — and reports JS errors with the React component stack. Point it at **our own OTel collector**, not at EAS Observe, so nothing about a courier leaves our infrastructure. `networkTraces` stays **off**; `sampleRate` is set low; `Observe.clientId` is the only identifier we ever send.
- **Errors: `@sentry/react-native@8.31.0` (client) → GlitchTip (server).** The client is MIT, verified on SDK 58 / RN 0.88 the same day we read it, and the only mature native+JS crash reporter for Expo. The server is **GlitchTip** (MIT, self-hostable, Sentry-compatible) because **Sentry's own server is FSL-1.1-Apache-2.0**, which our CONSTRAINTS.md forbids. DSN only in the client; no auth token; no session replay; no screenshot attachments (issue #6900 shows masking is not honoured).
- **Product analytics and flags: `PostHog/posthog` (self-hosted) + `posthog-js`.** Anonymous aggregate events only, no PII, no session replay, no identity resolution. The flag surface gives us a behaviour kill-switch. The RN SDK ships from `posthog-js` — **not** from the dead `posthog-react-native` repo.
- **API traces: OpenTelemetry Python** in `apps/api` + the **collector** (with the contrib processors that strip and redact). The JS SDK waits for the `hrTime()` clock-drift fix (opentelemetry-js #7217/#7218) and is web-only until then.
- **LLM traces: Langfuse (self-hosted)** — activated only when the voice path is live, pinned ≥ the RBAC fix, no "member" role, and the OTel SDK's "mutates returned response data" bug (#19094) reviewed before the voice pipeline depends on it.

**2. Testing — one tool for E2E and visual regression, and the two mutation gates that were only written down.**

- **Maestro stays** (`cli-2.11.0`, pinned) and grows `assertScreenshot`; **`reg-cli`** does the image diff locally. The screenshots of a courier's screen never leave our CI artefacts, and there is **no second vendor**.
- **Install Stryker and mutmut**, add the missing `pnpm mutation` script, and scope the run to the changed files as CONSTRAINTS.md says. A gate that has never run is not a ratchet.
- **Wire the 50× backtest into a nightly CI job** (never per PR — 50 iterations is a third of the monthly quota if it is per PR) and publish the artefact.

**3. CI/CD & OTA — GitHub Actions stays; EAS Update is the OTA; EAS is an add-on, never a replacement.**

- **GitHub Actions remains the CI.** EAS Build is used for the *signed store* build only; the PR pipeline stays on our own runners, as the founder's rule requires.
- **OTA: `expo-updates` + EAS Update**, with `eas.json` (`production`, `preview` channels), `runtimeVersion: { policy: "appVersion" }`, **two channels only**, a **10 % → 50 % → 100 % rollout** on every production publish, and `eas update:rollback` written into the runbook. **End-to-end code signing** is a Production-plan feature and therefore a founder-approval item; until it is on, the `preview` channel stays the only place a new bundle goes.
- **Self-hosting OTA is not now** — `expo/custom-expo-updates-server` has had no commit since 2025-11-05.
- **Supply chain: syft (CycloneDX SBOM) → grype + osv-scanner (scan) → cosign (sign + attest) → scorecard (weekly) → harden-runner (one line per job).** Renovate for dependency updates, CI-only, recorded in `docs/LICENSES.md`.
- **Re-pin every action** to a current SHA (`checkout` v4-era, `cache` v4-era, `upload-artifact` v3-era, `setup-node` v4-era, `codeql-action` v3-era) — the runner already warns on all of them, and `upload-artifact` v4+ changed the artefact layout, which our evidence upload depends on.

**4. The fallback for each decision.**

| Decision | Fallback if it fails |
|---|---|
| `expo-observe` | Send the same OTLP to EAS Observe (100 k events/mo free) or to our own collector only. The library is endpoint-agnostic, so this is a config change, not a code change. |
| GlitchTip | The hosted GlitchTip (free tier 1 000 events/mo, $15/mo for 100 k) — same protocol, same client, no code change. **Not** Sentry self-hosted (FSL). |
| PostHog | PostHog Cloud's free tier (1 M events/mo) with billing limits set to $0, or a second self-hosted PostHog on Oracle. **Not** Amplitude/Mixpanel: they would break the self-hosting rule. |
| OpenTelemetry | The OTLP protocol is the fallback *for itself*: any OTLP backend can be swapped behind the collector. |
| Langfuse | OTel + a trace backend (Jaeger, Apache-2.0) for the LLM spans, with `openllmetry` doing the instrumentation. |
| Maestro | `maestro-runner` (Apache-2.0, 100+ commits/90 d) is the drop-in-compatible successor. Detox and Appium are the deeper fallbacks but are heavier. |
| `reg-cli` | Maestro's own `assertScreenshot` can compare against a baseline without a second tool at all. |
| EAS Update | Keep a local `expo export` + a self-hosted update server (the `custom-expo-updates-server` reference) as the escape hatch. |
| EAS Build | Our own `gradlew assembleRelease` in CI already builds the APK — it is the path for the unsigned/internal build today, and the path that EAS replaces only for the signed store build. |
| GitHub Actions | Nothing replaces it (founder's rule). A self-hosted runner on Oracle is the *cost* mitigation, not a replacement, and it consumes the same quota from 2026-03-01. |
