# Parity — feature by feature against the 2026 market

Maintained per V4 §4. Base: `docs/product/COMPETITIVE_RESEARCH.md` and `docs/research/RESEARCH_2026_WAVE3.md`
(the 49-service parity matrix), refreshed with the 2026 entrants (Circuit/Spoke, Route4Me, Upper,
Routific, OptimoRoute, Onfleet, Beans.ai, MyRouteOnline, Straightaway, Zeo, Road Warrior, Google/Apple
Maps multi-stop, the NZ carrier driver apps).

**Status key** — `Have` (shipped) · `Better` (we do it better than the market) ·
`Planned (task)` (in the V3 task list) · `Skip (reason)`.

The **Spoke** column is mandatory (V4 §13.2): every family is compared with the number one NZ competitor, from docs/study/spoke/ (TEARDOWN, REVIEWS, BEAT-SPOKE, read 2026-10-20).

Task ids: **T4** LINZ data · **T5** offline maps · **T6** design · **T7.x** the product list in
`docs/archive/KICKOFF_V3_EN.md` · **T7.15** PIA, store assets, acceptance test, handover.

Reconciled 2026-10-26 (audit item B1): every row was read against what is on `origin/main`, and a row
may only say `Have` when the **Evidence** column names the merged PR or the CI run that put it there.
The two parity gaps the audit added — a **planned break** (TEARDOWN line 221) and **stop types** — are
rows 309 and 310.

**How a row earns its word:**

- **`Have`** — the feature named in the row exists on `main`, and the Evidence column names the merge.
  Where only half of a row shipped (the server half, or a screen half), the Evidence column says which
  half and names the task that finishes it: a `Have` is never a claim that a courier can use it end to
  end today (the app↔API wiring is audit item A1).
- **`Better`** — kept only where the row already argued we measurably beat the competitor, now with its
  evidence. No new `Better` row was invented in this pass; a claim that could not be proved was moved
  down to `Planned (task)`.
- **`Planned (task)`** — not on `main`. The Task column names the task that builds it: a T-number, or an
  audit item where that is the real remaining work. "Recorded, not scheduled" is not a status.
- **`Skip (reason)`** — a written decision not to build it; the reason is in the row.

**The counts are a gate.** `node scripts/ci/check-parity.mjs` counts the four words above (and the
words of the bug tracker's status column), prints the count and fails the build on a status that is not
one of them, on a `Have` row with no merged PR or CI run link, or on a table with no `Status` column.
The count is copied into `docs/status/PROGRESS.md` with every merge (audit item B1's done-when).

## Where we beat the market (the differentiators to protect)

Each claim below is carried by a `Better` row, and where a claim is not shipped yet its row stays
`Planned (task)` and says what is missing — the claim is the target, the row is the truth.

1. **Voice-first, hands-free** — the whole shift is runnable by voice (D2); the market's voice support
   is one-shot dictation at best.
2. **NZ address auto-correction with an explanation** — the D8 engine corrects, says what it changed
   and asks only when unsure; no competitor does this for NZ addresses.
3. **Door memory** — learned per LINZ address and read out on arrival.
4. **Template-based daily rebuild** — the driver's own route and rules, rebuilt in one tap.
5. **On-device privacy** — audio never leaves the phone by default; NZ Privacy Act 2020 PIA in T7.15.

## Rules

- A row may only leave `Planned (task)` when the task is merged **with evidence** in `docs/evidence/`, and its Evidence column names the merge.
- A row may only become `Skip` with a written reason (the product spec or an ADR).
- A `Have` row whose Evidence column is empty, or whose status word is not one of the four of the key, fails `scripts/ci/check-parity.mjs`.
- The count is produced by `node scripts/ci/check-parity.mjs` and is copied into `docs/status/PROGRESS.md` with every merge (audit item B1's done-when).
- The V4 Definition of Done requires no `Planned (task)` left in the must-cover families.
