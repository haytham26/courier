# Evidence — dependabot configured, and a cron staging smoke (BUG-223, audit 3i / C14)

**Step:** the 2026-11-05 audit's item 3i, finding C14 · **Branch:** `dependabot-cron-223` ·
**Date:** 2026-11-06

## What was broken

1. **No `.github/dependabot.yml` existed** — no ecosystem (the pnpm
   lockfile, the two `uv.lock` files, the GitHub Actions refs) was watched for
   updates at all. Version bumps arrived only when a human remembered.
2. **Nothing ran the staging smoke on a schedule** — `infra/smoke.sh` ran
   only inside the deploy leg, immediately after a deploy. A staging that
   rotted overnight (disk, certificate, a stale replica behind the edge) was
   found by the first courier of the day, not by a machine.

## What landed

### `.github/dependabot.yml` (version 2, all weekly)

- `github-actions` at `/`
- `npm` at `/` — this is a pnpm workspace; the `npm` ecosystem reads
  `pnpm-lock.yaml`
- `uv` at `/services/api` and `/services/courier-voice` — every directory
  that carries a `uv.lock`

Ecosystem support verified against GitHub's own configuration reference on
2026-11-06: `uv` is a supported `package-ecosystem` value, and the `npm`
ecosystem's supported lockfiles include pnpm v7–v12.

The file's comments carry the two rules a dependabot PR must follow:
**action PRs re-pin to the new tag's commit SHA** (`check-action-pins.mjs`,
BUG-222 — a tag ref fails the Floor guard), and **npm/uv PRs carry the
lockfile and the `docs/product/LICENSES.md` inventory** (regenerated by
`node scripts/ci/check-licenses.mjs --write`) in the same PR.

### `.github/workflows/staging-smoke.yml`

- Triggers: `schedule` cron `"5 18 * * *"` (18:05 UTC = 07:05 NZDT in
  November, before the first shift) **and** `workflow_dispatch`.
- `permissions: contents: read`; every `uses:` pinned to a 40-hex SHA.
- The staging secrets (`COURIER_STAGING_DOMAIN`, `COURIER_SMOKE_TOKEN`) are
  read **only in step-level `env:`** (BUG-100 / audit 3c — never job-level,
  never in a command line). A first step checks them and, when either is
  unset, prints a `::notice::` naming it and sets `configured=false` — the
  run **skips loudly**, like the deploy leg, until the founder sets them
  (FOUNDER_TODO).
- The smoke step runs
  `bash infra/smoke.sh --domain "$DOMAIN" --token "$TOKEN" --no-version
  --evidence smoke-evidence` — `--no-version` **by design**: a cron run is
  not a deploy, there is no just-deployed sha to prove, and the version
  check is the deploy leg's (audit item 3b). The deploy leg's smoke still
  runs it.
- The report (`smoke-evidence/smoke.md`) is uploaded as an artifact
  (`staging-smoke-report`, 14-day retention).

### The gate

`scripts/ci/check-staging-smoke.mjs` (a step in the `Floor guard` job) holds
both halves: dependabot version 2 with the three ecosystems, each weekly,
each `uv` entry pointing at a directory that really has a `uv.lock`; and the
workflow's cron + dispatch triggers, the `smoke.sh` call with `--domain`
`--token` `--no-version`, secrets only at step-level env, the skip-notice,
SHA-pinned actions, and `permissions: contents: read`. 14-case test.
