# C3's fourth parser slice — the register's own suburb vocabulary

**Date:** 2026-10-30 · **Owner:** the backend squad (address) · **Task:** C3's measure/fix/re-measure loop.

## What was measured, and with what

The same command every time, over the same index built from today's LINZ revisions:

```powershell
uv run --with httpx python scripts/data/fetch-linz.py --area christchurch --limit 400000
uv run --with httpx python scripts/data/fetch-linz.py --area waimakariri --limit 400000
uv run --with httpx python scripts/data/fetch-linz.py --area selwyn
uv run python scripts/data/build-linz-index.py --area christchurch   # and the other two
uv run --directory services/api pytest tests/test_linz_accuracy.py -v -p no:randomly
```

656,392 real addresses (Christchurch 225,295 · Waimakariri 236,205 · Selwyn 194,892), 120 sampled
per area with seed 20261020, 1,800 checks. The written report is
`docs/evidence/phase-2.3/linz-accuracy.md` — it is regenerated by the run, so the numbers there are
always the latest.

| Run | Accuracy | What changed |
|-----|----------|--------------|
| 2026-10-20, `92aba93` (git history) | **96.9 % (1745/1800)** | the baseline, over 656,044 addresses |
| 2026-10-30, before this slice | **85.2 % (1534/1800)** | the same engine and the same pipeline over today's revisions |
| 2026-10-30, after this slice | **96.9 % (1744/1800)** | 266 failures → 56 |

The per-case table of the latest run is in the report; the two runs above differ in the sample only by
the 348 addresses LINZ has added since 2026-10-20 (1744 vs 1745), which is the honest comparison:
before and after, same data, same command, one session.

## What the 85.2 % run printed, and what each class was

A classifier over every failure (`sample: 360 addresses; 112 of them (31 %) sit on a road that spans
several suburbs`):

1. **`'<road>' runs through several suburbs` — the majority of the loss.** The driver had NAMED the
   suburb (`24 Dublin Street, Christchurch Central`), and the engine still asked which suburb, with
   the named one among the options. `nz_address.parse` only hands the tail after the street type to
   the engine when the parser's own `CHCH_SUBURBS` list recognises it — 45 Christchurch suburbs,
   which do not include `Christchurch Central`, `Lyttelton`, `Prebbleton`, `Rolleston`, `Lincoln`,
   `Kaiapoi` or `Diamond Harbour`. The tail was therefore discarded, and the engine's
   `_match_suburb(hint, road_suburbs)` — which would have matched it against the suburbs the road
   really runs through — was never given a hint.
2. **The spoken house number after a unit** (`unit 1 seven Michelle Road Wigram` → house number
   "seven", 40 failures). `_words_to_digits` converts a LEADING run of number words only, because a
   road's own name may be a number word (`Two Chain Road`, C3's third slice). Once `unit` had been
   emitted the run was over, so the number the courier actually said was never converted.
3. **A road whose name starts with a letter** (`19 O'Leary Street, Hoon Hay` → house number `None`).
   The spoken-suffix heuristics use `\b`, which also holds between a letter and an apostrophe, so
   "19 O" was glued into "19O'Leary" and the number was lost.
4. **The suburb was cut out of the road name** (`2 Skara Brae, Prebbleton` → road "Skara"). With no
   street type spoken, the tail was tried longest-first and "brae prebbleton" fuzzy-matched
   `Prebbleton` at SequenceMatcher 0.83, so the road's own second word was eaten.

## The fix, red first

`services/api/tests/test_suburb_vocabulary.py` — 12 tests, one per class, each quoting the failure it
was written against. On the unfixed tree: **9 failed, 3 passed**. Green after:

- `AddressStore.suburbs()` — the register's own vocabulary, on the protocol and on both stores
  (in-memory caches the set; the SQLite store runs `SELECT DISTINCT suburb` once). The engine passes
  it to `nz_address.parse`, so the parser can tell a suburb from the rest of a road name for every
  suburb we serve, not only the 45 it had hardcoded.
- `parse` sets `suburb_hint` for **every** tail after the street type, whether or not its vocabulary
  knows it: the store decides, not the list. `match_suburb_tail` tries the longest candidate first,
  because a courier repeats the city ("… Christchurch Central, Christchurch").
- `_spoken_number_after_unit` converts the run of number words that follows the unit (and only it).
- The two spoken-suffix heuristics require the letter to be a token of its own (`(?=\s|$)`).
- The no-street-type branch takes the shortest **exact** tail first and only falls back to fuzzy.

The mutation check (PLAYBOOK §14.5, until the B4 floor covers these files): flipping
`for exact_only in (True, False)` to `(False, True)` in `nz_address.parse` turns
`test_a_suburb_the_hardcoded_list_does_not_know_is_taken_from_the_register` red; dropping the
`hint = tail` assignment turns five of the twelve red.

## The baseline's own number, and the one hypothesis that would explain it

The 2026-10-20 baseline (96.9 %) was produced by the same engine — `git diff 92aba93 HEAD` over
`address_correction.py` is formatting and docstrings only, 91 % similarity — and by the same pipeline
(`build-linz-index.py` is byte-identical in logic). Today's fresh index carries the same composition
(**31.4 %** of Christchurch rows sit on a road that spans several suburbs in the full index, **30.7 %**
in the first 200,000 rows, i.e. in the 2026-10-20 truncated index), so the class that cost 266
failures today cannot have been absent then.

**Hypothesis (unproven, recorded as such):** the 2026-10-20 run read a `data/linz/` copy whose
`suburb_locality` was emptier than today's, so a road had one suburb and the question never fired.
LINZ has since populated the field more completely. The data of that day is not retrievable — the
service serves today's revisions — so the hypothesis cannot be tested from here, and it is NOT the
basis of any claim above. What is measured is the 2026-10-30 pair: 85.2 % before, 96.9 % after, one
data set, one command.

## What the remaining 56 failures are

- `287C/28 Cathedral Square` — the unit is answered as `28C`: the unit's letter is dropped when the
  number follows a slash (C3's first slice covers `255C/28`, this is its twin).
- `GB/87 Kilmore Street` — a unit with no digits at all before the slash.
- `87 Kilmore Street` for `GB/87` — same class.
- `928 Two Chain Road Swannanoa` (spoken) — the road's own number word is still read as the house
  number in the spoken form.
- `648 No 10 Road Swannanoa` — a road whose own name carries a number, no street type.
- `71 St Andrews Square Strowan` — "St" is read as the street type and the road name is lost.
- `14 Deal Street Wigram` (misspelled) — difflib picks `Dale Street` in Kaiapoi over `Deal Street`.
- `15 Caspian Street South New Brighton` — a multi-word suburb whose first word is also a road
  direction; the direction is kept on the road.
- `84 Oxford Street Lyttelton` for `84 Oxford Terrace` — the street type is lost in the misspelling.

Each is a separate slice, in the order C3 names them (the parser: units and flats, RD, rural
numbers, ranges, te reo macrons, typos and abbreviations).
