## BUG-067 — the map-pack workflow could not start, and BUG-064's guard took the blame

- **The symptom, twice misread.** 65 runs, from PR #43's first push onward, each failing in **0
  seconds** with `This run likely failed because of a workflow file issue`: no jobs, no steps, no log,
  no annotation naming the line.
- **The line.** `if-no-files-found: error` sat at a **step's own level**, a sibling of `uses:` and
  `with:`. It is an **input of `actions/upload-artifact`**, so it belongs **inside `with:`**. An unknown
  key at a step makes GitHub refuse the whole workflow file, on every event, before any job exists.
- **GitHub states it precisely when asked to dispatch:**
  `failed to parse workflow: (Line: 172, Col: 9): Unexpected value 'if-no-files-found'`.
- **The same file also carried the dispatch-only `inputs` context** in three expressions — a second,
  latent defect of the same class — and `.github/workflows/store-ready.yml` carried it in its release
  lane. Both fixed, with `scripts/ci/check-workflows.mjs` (13 tests, wired into the Quality gates) as
  the gate that fails on either.
- **Why it took a bisect, not a theory.** My first theory was the `inputs` context; it was shipped,
  the run still failed, and the bisect named the key. The register carries the true root cause, and
  the week log says the theory was wrong.
- **The proof runs.** Two dispatches and the merge commit's own push run each went through checkout,
  the pinned Java runtime, the tools, the extract and the plan, and stopped only at the **licence
  gate**, which refuses by design until the founder confirms Geofabrik's terms
  (`--confirm-offline-use`, already open in FOUNDER_TODO).

## B3's first item — the WebSocket token out of the query string (merged, PR #75)

`services/api/app/auth/websocket.py` gains `identify` (the header **or the first `auth` message**,
never the query string), `refuse` (the reason in an `error` frame, then close **4403**) and
`CLOSE_UNAUTHENTICATED`. Seven tests in `tests/auth/test_websocket_auth.py` drive both through a fake
handshake and a real verifier over a real key pair: the header still works; the first message may
carry the token; **a token in the query string is refused**; no token, an invalid token, and a first
message that is not an `auth` frame are all refused with the words the caller needs; and `refuse`
closes with 4403 and names the reason.

The route's half is the next step, and the evidence folder names its shape precisely: with the route
accepting the socket before it identifies the handshake, the two refusal tests read an `error` frame
and then a second frame on a socket the module has already closed, and that second read blocks. The
fix is that shape with one frame read per refusal, and the close code proven in the module's own test
— five minutes **with a machine where the suite runs**.
